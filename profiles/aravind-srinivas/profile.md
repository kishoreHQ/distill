## E. Implementation playbooks

### Playbook 1: "AI-complete" niche product with a strict-grounding RAG core (derived from [S3][S4][S7][S8])
- **Problem:** choosing an AI product that won't be flattened by the next model release.
- **Preconditions:** a narrow domain where you can get good sources (e.g. Kishore's Linux/DevOps docs, runbooks, CVE feeds) and access to an LLM API.
- **Tools:** retrieval (search API or vector DB), any frontier LLM, citations in the UI, an eval set of real questions.
- **Steps:** 1) Pick a narrow edge where better models automatically mean a better product. 2) Answer only from retrieved sources, with citations, and refuse when sources are thin. 3) Test latency on a bad connection. 4) Ship early and watch for usage without prompting (holidays or weekends). 5) Add follow-ups or suggested questions to deepen sessions.
- **Expected output:** a cited answer engine for one domain.
- **Cost:** low (API usage). **Time:** 1–3 weeks for an MVP. **Complexity:** medium.
- **Risks:** source licensing and permissions (see the crawler controversy, [S13]); hallucinations if grounding isn't enforced.
- **Success metric:** % of answers with valid citations, repeat weekly users, refusal correctness.

### Playbook 2: Agent "council" plus safe-fetch for automation reliability (derived from [S16][S17][S18][S24])
- **Problem:** single-model agents make silent errors and get prompt-injected by fetched pages.
- **Steps:** 1) Run 2–3 models on high-stakes tasks and have a chair model reconcile them. 2) Score every fetched page or tool output for prompt injection before the agent sees it. 3) Run agent tools in a sandbox with least privilege. 4) Track success rate over long step counts, not demo runs.
- **Cost:** 2–3× tokens on council tasks. **Complexity:** medium.
- **Risks:** cost blow-up; false sense of safety.
- **Success metric:** error rate on audited runs; injection attempts blocked.

### Playbook 3: Treat complaints as roadmap (derived from [S16][S20][S21])
- Log every complaint and feature request per vertical. Ship the most frequent fix fast and announce it publicly. Choose defaults (models, UX) by retention data, not opinion. Metric: complaint-to-ship time and retention change after each default switch.
